# 1. Harness Engineering（ハーネス・エンジニアリング）

## ひとことで
**LLM の「周りの仕組み」を設計すること。**
モデル自体は変えずに、モデルが安全・確実に仕事をできる環境（＝ハーネス、馬具）を作る。

> Agent = Model + Harness
> 同じモデルでも、ハーネス次第で「使えない」から「本番運用できる」まで変わる。

## ハーネスの構成要素

| 要素 | 役割 | 例 |
|---|---|---|
| コンテキスト設計 | モデルに何を見せるか | システムプロンプト、ツール一覧、関連ファイル、CLAUDE.md |
| ツール定義 | モデルが使える「手足」 | 関数スキーマ、MCP サーバー |
| 出力検証 | モデルの出力を信用せずチェック | JSON パース、スキーマ検証、型チェック |
| 権限・ガードレール | やってはいけないことを止める | 読み取り専用、承認フロー、サンドボックス |
| リトライ／エラー回復 | 失敗をフィードバックして再試行 | エラーメッセージを文脈に追加 |
| 観測性 | 何が起きたか追えるようにする | ログ、トレース、コスト計測 |

## なぜ重要か
- モデルは確率的。**たまに壊れた出力・危険な要求を出す** 前提で設計する必要がある。
- モデルの改善を待つより、ハーネスの改善の方が **すぐ・安く・確実に** 効く。
- Claude Code / Cursor などのコーディングエージェントの差は、モデルだけでなくハーネスの差でもある。

## デモ（約1分）
```bash
python demos/harness_demo.py
```

**シナリオ**: 「tmp フォルダの中身を確認して」というタスクに対し、モデルが
1. 説明文混じりの壊れた JSON を返す
2. 危険な `delete_files("/")` を要求する
3. フィードバックを受けて `list_files("./tmp")` に修正する

| | 結果 |
|---|---|
| (A) ハーネスなし | 危険なツールがそのまま実行される 💥 |
| (B) ハーネスあり | 検証 → 権限で拒否 → エラーを返して再試行 → 安全な操作だけ実行 ✅ |

### 話すポイント（台本）
1. 「モデルは**まったく同じ**です」(A) を実行 → 危険な操作が通ってしまう
2. (B) を実行 → `✋` の行を指して「JSON 検証」「権限チェック」が止めている
3. 「エラー内容をモデルに返すと、モデルは自分で直す」→ 3回目で成功
4. 締め: **「賢いモデル」より「良いハーネス」が信頼性を決める**

### コードの見どころ
- `validate()` … JSON / スキーマ / 権限の三段チェック
- `ALLOWED_RISK` … ポリシーを1行で切り替えられる（`{"read", "write"}` にすると削除も通る）
- `prompt += f"\n前回のエラー: {err}"` … エラーを文脈に戻すフィードバック

## 発展
- ツール呼び出しは Claude API の `tools` パラメータ（構造化出力）で受けると、パース失敗自体を減らせる
- 危険な操作は「拒否」ではなく「人間の承認待ち」にする（Human-in-the-loop）
- Claude Code の hooks / permissions はハーネス設計の実例
