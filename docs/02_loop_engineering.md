# 2. Loop Engineering（ループ・エンジニアリング）

## ひとことで
**エージェントが「試す → 確かめる → 直す」を繰り返す反復処理を設計すること。**

```
        ┌──────────────────────────────────────┐
        ▼                                      │
   Observe ──▶ Think ──▶ Act ──▶ Verify ──(失敗)┘
  (状況把握)   (計画)   (実行)   (検証)
                                   │
                                (成功 / 予算切れ / 停滞)
                                   ▼
                                 STOP
```

一発で正解を出させるのではなく、**検証可能なフィードバックを使って収束させる**。

## 設計ポイント

| 観点 | 問い | 例 |
|---|---|---|
| 検証器 (Verifier) | 何をもって「できた」とするか | テスト、型チェック、lint、別モデルによるレビュー |
| フィードバック | 失敗情報をどう次に渡すか | エラーメッセージ、失敗したテストケース、差分 |
| 停止条件 | いつ止めるか | ✅成功 / ⛔最大反復回数 / ⛔進捗なし / ⛔コスト上限 |
| 状態管理 | 反復間で何を覚えておくか | 試した案の履歴、ベストスコア |
| エスカレーション | 止まったら誰に渡すか | 人間に相談、別戦略に切り替え |

## なぜ重要か
- 難しいタスクほど一発正解は難しい。**検証できるなら、反復すれば精度は上がる**。
- 停止条件がないループは「無限ループ」「コスト爆発」になる。止め方の設計が本体。
- テスト駆動のコーディングエージェント、Deep Research、Ralph ループなどは全てこのパターン。

## デモ（約1分）
```bash
python demos/loop_demo.py
```

**シナリオ**: バグのある `average()` を修正する。テストは3件（空リストのケースを含む）。

| | 結果 |
|---|---|
| (A) 一発回答 | `+ 1` は直したが、空リストで `ZeroDivisionError` ❌ |
| (B) ループ | iter1: 0/3 → iter2: 2/3 → iter3: 3/3 ✅ で自動停止 |

### 話すポイント（台本）
1. (A) を実行 → 「パッと見正しそうだが、テストすると落ちる」
2. (B) を実行 → `observe` 行の合格数が **0/3 → 2/3 → 3/3** と増えていくのを指す
3. `think` 行 → 「テストの失敗内容がそのまま次のヒントになっている」
4. `stop` 行 → 「成功したら止まる。止まらない場合も上限・停滞検知で止まる」
5. 締め: **品質はモデルの賢さ × ループ設計（検証・フィードバック・停止条件）**

### コードの見どころ
- `run_tests()` … Verifier。ここの質がループ全体の質の上限
- `feedback = "; ".join(fails)` … 失敗を次の入力へ
- 停止条件①②③ … コメントで3種類を明示

## 発展
- 検証器を LLM にする（LLM-as-a-judge）とテストがないタスクにも適用可能。ただし検証器自体の信頼性に注意
- 複数案を並列に生成してベストを選ぶ（best-of-N）とループを組み合わせる
- Claude Code の `/loop` やエージェント SDK のターン上限は、ループ設計のパラメータ
